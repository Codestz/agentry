# 05.1 — Extending the Roster: the capability layer

> **Status:** ✅ Signed (all sections executed) · **Date:** 2026-06-14 · signed 2026-06-15 · **Scope:** the per-agent and per-skill
> *capability* layer that sits on top of the roster (doc 05) — which Claude Code agent features Agentry
> actually gets **as a plugin**, the frontmatter standard, lifecycle-event emission for the Workbench,
> and deeper craft via multiple references. Born from dogfooding: two capability bugs surfaced (agent
> frontmatter silently dropping fields; per-agent hooks blocked for plugins), so this doc records the
> **real** matrix and leads the extension so we build on fact, not assumption.

---

## 0. Why this doc exists

Doc 05 defines *who* the specialists are. This doc defines *what capabilities they carry* and corrects
two things dogfooding proved wrong:

1. **The agent frontmatter was malformed** — a plain multi-line `description:` with `<example>` blocks
   breaks YAML at the first inline colon, so **every field after it (`model`/`color`/`skills`) was
   silently dropped.** The whole roster ran with **no preloaded skills**, no color, default model. Fixed
   (block-scalar description); §2 makes it the standing convention.
2. **Per-agent hooks don't work for us.** Plugin subagents **ignore** `hooks`/`mcpServers`/`permissionMode`
   frontmatter (security). The Workbench "see agents working" seam must use **plugin-level** lifecycle
   hooks instead (§3).

> Governing principle: **a capability we *assume* but don't *verify* is a silent failure.** Verify each
> field actually parses and takes effect (parse the frontmatter, don't eyeball the text).

---

## 1. The plugin-subagent capability matrix

Agentry ships as a plugin (the repo root *is* the plugin), so only the fields that apply to **plugin
subagents** are usable. (Source: `.docs/anthropic/agents.md`.)

| Frontmatter field | Applies to a *plugin* subagent? | Agentry uses it |
| :--- | :--- | :--- |
| `name`, `description` | ✅ required | ✅ |
| `tools` / `disallowedTools` | ✅ | ✗ (capability-first — no allowlists, doc 05) |
| `model` | ✅ | ✅ `inherit` |
| `skills` | ✅ — **injects full skill content at startup** | ✅ (the craft-preload guarantee) |
| `color` | ✅ — `red·blue·green·yellow·purple·orange·pink·cyan` only | ✅ distinct per agent |
| `memory` | ✅ | ✗ **deliberately** — `@agentry/memory` is the single memory substrate; a second per-agent store would compete |
| `isolation: worktree` | ✅ | ✅ situationally (parallel implementers, doc 05/planning) |
| `maxTurns`, `effort` | ✅ | ✗ (not needed yet) |
| **`hooks`** | ❌ **ignored for plugin subagents** | use plugin-level hooks (§3) |
| **`mcpServers`** | ❌ ignored | MCP wired in `plugin.json` |
| **`permissionMode`** | ❌ ignored | n/a |

**The block-scalar rule (non-negotiable).** A multi-line `description` with `<example>` blocks **must**
be a YAML block scalar (`description: |`, body indented 2 spaces), or every field after it is dropped.
Verify by parsing, not by reading.

## 2. The frontmatter standard (every agent)

```yaml
---
name: <agent>
model: inherit
color: <one of the 8 valid colors — distinct per agent>
skills: [<craft skills to preload>]
description: |
  <one-line "use this agent when…"> Examples:

  <example> … </example>
---
<system prompt body>
```

- **Clean key:values first, `description: |` last** — so the example-laden text can't break the parsed
  fields.
- **`skills:` is the craft-preload guarantee** — the listed skills' full content is injected at startup,
  so the specialist always has its craft, not just when it remembers to load it. Each agent lists the
  skills that *are* its craft (architect → `architecting, planning`; verifier → `reviewing, integrating`; …).
- **Colors (distinct identity):** architect=blue · designer=purple · explorer=cyan · implementer=green ·
  librarian=yellow · product-owner=orange · researcher=pink · verifier=red.

Applies to the **entire roster — dev and product agents alike.**

## 3. Lifecycle events → the Workbench seam (corrected)

The Workbench V1 "see agents working" seam (doc 08 §5/§6) needs a run's agent lifecycle in
`events.jsonl`. Per-agent frontmatter hooks are **out** (§1). The mechanism is **plugin-level hooks in
`hooks/hooks.json`**:

- **`SubagentStart`** (matchable by agent type, receives `agent_type`) → emit a `WorkEvent`
  `{kind:"agent-started", agent}`.
- **`SubagentStop`** → emit `{kind:"agent-done", agent, …}`.

These fire in the main session, are purpose-built for the lifecycle, and **work for plugins** (the
`SessionStart` primer already proves the plugin-hook channel). The dep-free `.mjs` pattern of
`session-start-prime.mjs` is the template; reuse the `WorkEvent` contract already in
`@agentry/core` (extend additively only if needed).

> **Still an open fork (decide in that task's spec/plan, not here):** a hook fires per-event but doesn't
> know *which* `.agentry/work/<id>/` the event belongs to. Resolve it with an explicit signal (e.g. a
> conductor-written "active work" marker), **not** a fragile "newest-mtime folder" heuristic. This is the
> exact decision the earlier one-shot attempt guessed wrong — it earns a spec + plan gate.

## 4. Deeper craft via multiple references

Skills use **progressive disclosure** — `SKILL.md` loads on trigger; `references/*` load only when
pointed to, so adding references is **cheap until used.** Each skill currently has ~1 reference; several
carry enough craft to justify more. Add a reference when there's a real body of craft to disclose, not to
pad.

| Skill | Add reference | Why |
| :--- | :--- | :--- |
| `conducting` | **`judgment`** (evaluating uncertainty · evaluating complexity · thinking as a senior) | right-sizing depth is the highest-leverage, most-failed judgment; today's "hardest-signal-sets-the-floor" rule half-seeds it |
| (others) | as the fragility audit (§5) finds | only where a SKILL.md is carrying depth it should disclose |

---

## 5. Roster fragility audit (the parked sweep)

A standing pass over every agent + skill for the **gate-skip class** of fragility (flat guidance with no
override · one-directional bias · reactive-not-pre-flight · narrow triggers · skippable imperatives ·
guess-instead-of-decide · no self-catch). The `conducting` routing rubric was the first instance found and
fixed (hardest-signal-sets-the-floor). The audit applies the same lens roster-wide and hardens the durable
content — **fix the skill/agent, never the operator.**

## 6. Acceptance (what "done" looks like)

- Every agent's frontmatter **parses** with `name/model/color/skills/description` present; colors distinct
  and valid; `description` a block scalar. *(✅ landed 2026-06-14.)*
- `SubagentStart`/`SubagentStop` plugin hooks emit `WorkEvent`s to a correctly-routed `events.jsonl`
  (work-id resolved by a session-keyed pointer the PostToolUse binder writes — ADR-001), dep-free,
  additive, silent in non-Agentry repos. *(✅ landed 2026-06-15, `bd68668`; live-fired after relaunch.)*
- `conducting` carries a `judgment` reference; the fragility audit's high-severity findings are fixed.
  *(✅ landed 2026-06-15, `dd5e6e5` — gate-skip sweep of all 8 agents + 13 skills, HIGH+MED+LOW, plus
  `search-craft.md` + `judgment.md`; independent verifier MEETS.)*
- No use of `hooks`/`mcpServers`/`permissionMode`/`memory` frontmatter on plugin agents. *(✅ holds —
  `check-plugin` warns on a `tools:` allowlist; the roster sweep introduced zero frontmatter drift.)*
